# Данные обычных запусков /i

Статус: реализован локальный сборщик и отчёт. Он наблюдает выполнение, но не
меняет prompt, модель, effort, выбор проверок, permissions или правила review.
Новых Pi-команд и обязательных действий перед запуском нет.

## Как работает

Новый `/i` начинает запись только после успешного выбора модели и проверки
аргументов. `/i --next` и совместимый `/n` также учитываются; `/b`, `/bh`, обычные
сообщения вне `/i` и исторические сессии автоматически не импортируются.
Граница записи — от команды до `agent_settled`, а не отдельного model turn.
`workflow_status finishing` очищает footer, но не обрывает сбор последнего ответа.
Смена сессии и shutdown дают `interrupted`, новая `/i` вместо незавершённой —
`superseded`. Повторное settlement не создаёт вторую запись.

При старте записывается checkpoint `started`. При завершении тот же файл
атомарно заменяется итогом. Если Pi аварийно закрыт, checkpoint остаётся без
зафиксированного завершения: это не доказательство, что процесс ещё работает,
и такой запуск исключён из медиан времени и сумм стоимости завершённых запусков.

Каталог: `${XDG_STATE_HOME:-~/.local/state}/pi/workflow-metrics/`; переопределение
`PI_WORKFLOW_METRICS_DIR`. Записи `<run-id>.run.json`, отдельная явная оценка
`<run-id>.feedback.json`, автоматически обновляемые `summary.json` и `summary.md`.
Новые каталоги имеют mode 0700, файлы — 0600. Ошибки записи дают не более одного
предупреждения за загрузку расширения и не прерывают выполнение. Сбор отключается
через `PI_WORKFLOW_METRICS=0`; перезапуск/reload нужен после обновления расширения. Для уже развёрнутого
Stow-пакета нужна ссылка `~/.config/pi/lib` на `pi/.config/pi/lib`; она установлена
на этом Mac. Package-local `.stow-local-ignore` оставляет документацию, scripts,
tests, experiments и runtime node_modules в репозитории, не линкуя их в `$HOME`.

Каждый запуск имеет отдельный файл: параллельные Pi-процессы не дописывают общий
JSONL и не перезаписывают чужие записи. Сводки — производный best-effort кеш:
параллельное обновление может временно оставить старый снимок. Скрипт отчёта
каждый раз пересчитывает сводку из записей. При чтении выбираются последние
200 файлов по времени старта; повреждённые записи показываются отдельным числом.
История сохраняется целиком, по несколько килобайт на запуск, без auto-delete.
Ограничение 200 относится к отчёту, а не к объёму хранения.

## Что именно измерено

- `workflowRevision` — хеш исходников workflow и сборщика при загрузке.
- `route` — начальные provider/model/thinking. Смены модели или effort во время
  запуска отмечаются числом `routingChanges`, такие строки не представляют один
  неизменный маршрут. Для разных версий и начальных маршрутов — отдельные группы.
- `wallMs` — монотонное время от команды до окончания; `uiWaitMs` — ожидание
  блокирующих extension UI prompts; `nonUiWallMs` исключает только это ожидание,
  но не равен CPU-времени или времени inference.
- `parentUsage` — usage завершённых assistant-сообщений; `helperUsage` — usage
  структурированных результатов subagent. Один результат `runId/index` считается
  один раз. Session totals не прибавляются, поскольку SDK уже включает детей.
  Helper results без usage отмечаются пропуском стоимости. Не вернувшиеся дети,
  compaction и неотданные usage могут отсутствовать: это наблюдаемая оценка,
  не подтверждённый счёт провайдера. Ноль не гарантирует бесплатное выполнение.
- `toolCalls` — фиксированные категории инструментов, неизвестные имена — `other`;
  `phases` — переходы по фиксированным workflow-фазам; `modelErrors` — ошибки
  модели, включая те, после которых работа успешно продолжилась.
- `checks` — категории tests/build/lint для распознанных одиночных shell-команд.
  Учитываются обращения, успешные/ошибочные ответы инструментов, известные
  структурированные exit codes и отсутствие результата. Распознаются также фиксированные display wrappers: `2>&1`, `| tail -N`
  и `; echo "EXIT_CODE=$?"` (имя метки может отличаться). Они показывают вызов проверки,
  но их shell exitCode не подменяет exitCode проверки. Другие compound-команды,
  пайпы, строки в кавычках и логи не анализируются: распознавание неполное.
  Pi 1.2.0 штатно не возвращает exitCode в successful bash details, поэтому он
  остаётся unknown; tool success не подменяет exit code отдельной проверки.
- `quality` — всегда `unverified` без отдельной явной оценки. Зелёные проверки,
  финальное сообщение модели и `finishing` не меняют её на accepted.

В файлах нет prompt, ответов, raw commands, stdout/stderr, исходников, имён
issues, путей проекта/сессии, credentials или персональных данных задачи.
Проект/сессия — сокращённые SHA-256 псевдонимы, не гарантия анонимности.
Время и названия моделей остаются локальными метаданными. Model usage и footer
обрабатываются без сохранения содержимого сообщений. Существующие Pi-session
логи не изменены: их собственная политика хранения остаётся прежней.

## Отчёт и оценка результата

```sh
node pi/scripts/workflow-report.mjs
node pi/scripts/workflow-report.mjs --feedback <run-id> accepted
node pi/scripts/workflow-report.mjs --feedback <run-id> needs-fixes contract
node pi/scripts/workflow-report.mjs --feedback <run-id> unverified
```

Необязательная причина: `contract`, `tests`, `scope`, `evidence`, `other`.
Оценка относится к конкретному ID и записывается отдельно после независимой
приёмки; модель не должна выставлять accepted по собственному финальному ответу.
Это явное локальное наблюдение, а не криптографически подтверждённое мнение
человека. Обновление оценки не меняет запись выполнения. Оценка ещё не
завершённого запуска, неизвестного ID и произвольные тексты отклоняются.

Повторные распознанные тестовые команды — сигнал посмотреть причины, а не
доказательство лишних full-suite прогонов: это могут быть разные целевые тесты
или проверка исправления. У разных задач разные сложность и обязательные checks.
Отчёт не делает причинных выводов и не меняет режимы автоматически. После серии
реальных задач полезно выбрать одну повторяющуюся подтверждённую проблему,
предложить одну правку и проверить её на соответствующих случаях.

Неформальные продолжения и исправления после `agent_settled` автоматически не
приписываются предыдущему запуску. Параллельное вмешательство в уже активную
задачу через новую `/i` также не изолирует стоимость двух задач: `superseded`
нужно рассматривать отдельно. Отчёт не заменяет controlled A/B.

## Проверки

```sh
node pi/tests/workflow-commands.mjs
node --test pi/tests/workflow-metrics.mjs pi/tests/workflow-metrics-integration.mjs
```

28 прежних command/route checks; 12 сценариев коллектора/отчёта и 3 сценария
через установленный Pi loader. Проверены checkpoint/settlement, последний ответ,
ошибки и восстановление, пауза UI, приватность, file modes, fail-open запись,
раздельные usage/dedupe помощников, неизвестные exit codes, незавершённые checks,
explicit feedback, повреждённые записи, окно 200 и параллельные экземпляры.
Скрипт рассчитан на Node с нативным TypeScript stripping (проверен на 22.21.1 и
26.11.1), без новых зависимостей.

Живой RPC smoke хранится отдельно от обычного журнала:
`/Users/doc/notes/pi-mode-comparison/2026-10-14-workflow-metrics-smoke/`.
Он подтверждает событийную интеграцию и usage, но не улучшение качества моделей.
