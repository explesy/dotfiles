# Проверка OpenCode Free → Pi

Проверено 20 октября 2026 года: Pi **1.3.0**, OpenCode **2.0.32**,
`opencode-pi` **1.4.0**, модель `opencode/deepseek-v4.1-flash-free`.

**Выбираемая модель Pi через этот мост пока не работает.** Клиентские ошибки
исправлены в экспериментальном патче, но запросы моста отклоняются сервисом
с HTTP 403 `FreeTierError`. Штатный OpenCode CLI с собственными инструментами
успешно выполняет задания на этой же бесплатной модели.

Это исследовательский артефакт. Расширение не установлено в активный Pi.

## Что исправлено

`compatibility.patch` применяется к npm-архиву `opencode-pi@1.4.0`:

1. Pi 1.3 передаёт системные инструкции, именованные секции и изменения
   инструментов через сообщения `role: "system"`. Старый сериализатор принимал
   такое сообщение за ответ ассистента и падал на `message.content.map`.
   Патч использует `normalizeContext`, `getCurrentSystemPrompt` и
   `getCurrentTools`, затем передаёт мосту актуальную инструкцию и набор tools.
   При изменении инструкции или tools существующая логика начинает новую
   сессию OpenCode.
2. Сериализация перенесена внутрь обработки ошибок, чтобы ошибка подготовки
   запроса завершала поток провайдера, а не весь процесс Pi.
3. Убрана ручная регистрация через устаревший `registerApiProvider`.
   Используется публичный `pi.registerProvider(..., { streamSimple })`.
4. Для OpenCode v2 создаётся JSON-конфигурация `agents` с новым массивом
   `permissions`. Старый Markdown с `permission` остаётся для v1.
5. Запуск v2 использует штатный общий сервер OpenCode вместо нового сервера
   на каждый запрос. Проверяется конкретная временная директория через
   `location[directory]`; перед запросом ожидается загрузка агента и
   подтверждается запрет всех его собственных инструментов.

В измеренной версии OpenCode первый ответ нового сервера `/api/agent` был
пустым; нужные агенты появлялись позднее. Это наблюдение, а не гарантия
документированного порядка загрузки.

Патч сохраняет строгий запрет инструментов OpenCode: исполнением tools
в архитектуре исходного моста должен владеть Pi. Заголовки, идентификаторы
клиента и HTTP-запросы к модельному backend не подменяются.

## Результаты реальных запросов

| Сценарий | Результат |
| --- | --- |
| Обычный `opencode run` на Free, короткий текстовый запрос | Получен `OPENCODE_CONTROL_OK` |
| Pi + исправленный мост + отдельный агент OpenCode с запретом tools | HTTP 403 `FreeTierError` |
| Pi + исправленный мост + стандартный агент `build` с запретом tools | HTTP 403 `FreeTierError` |
| Обычный CLI, стандартный `build` с запретом tools, простой текстовый запрос без контекста Pi | HTTP 403 `FreeTierError` |
| Обычный CLI, собственные инструменты OpenCode доступны | Реальные вызовы `read` и `write`, получен `NATIVE_TASK_OK` |

Последняя задача выполнялась только во временной директории: прочитать
`input.txt` с `value=19`, записать удвоенное значение в `answer.txt`.
Файл независимо проверен: байты **`38\n`**. В событиях двух инструментальных
шагов OpenCode указал `cost: 0`; это не отдельная проверка биллинга аккаунта.

Серверный отказ:

```json
{
  "status": 403,
  "type": "FreeTierError",
  "message": "OpenCode's free tier can only be used from within OpenCode. Download it at https://opencode.ai and keep building."
}
```

Точное условие серверной проверки не установлено. Контрольный запрос
показывает, что отказ воспроизводится и без сериализации Pi, при отключённых
tools OpenCode. Это исключает исходный TypeError как оставшуюся причину.
Другие способы интеграции Pi этим исследованием не исключены.

## Локальные проверки

- TypeScript strict: исходник и тесты с реально установленными SDK **1.3.0**.
- Адаптированный исходный набор: **80/80** тестов.
- Дополнительные регрессии Pi 1.3: **3/3** — изменения системных секций и tools,
  старые поля `systemPrompt`/`tools`, вызов Pi-инструмента из нормализованного
  transcript на подставном OpenCode.
- Патч проверен на применимость к исходному npm-архиву.

Тесты с подставным CLI проверяют локальные контракты. Они не доказывают
работу Free-модели через Pi. Живой цикл Pi tool-call → результат → ответ,
продолжение сессии моста, изображения, предел контекста, качество и
устойчивость к лимитам остались непроверенными из-за серверного отказа.

## Вариант дальнейшей интеграции

Подтверждённая рабочая основа — штатный OpenCode CLI как отдельный
исполнитель задачи. Расширение Pi могло бы передавать ему явно указанную
задачу и рабочую директорию, получать события, итоговый ответ и сведения
об изменениях. Инструменты и разрешения тогда исполняет OpenCode; Pi
сохраняет роль основного агента. Это другой контракт, требующий отдельного
согласования перед реализацией.

До оформления такого расширения нужны: реальный запуск из Pi, обработка
отмены и таймаута, передача ошибок без ложного успеха, границы рабочей
директории, проверка продолжения и отсутствие автоматической подмены
Free на платную модель.
