EXPERIMENTAL ORCHESTRATION (`/ix`). Execute only the concrete task below. Keep the selected main model and thinking level. Do not invoke `/n`, `/i`, `/p`, or `/ox`, select another issue, change model/role/permission configuration, or advance a backlog.

TASK: ${ARGUMENTS:-Use the concrete task already specified in this conversation. If the task is ambiguous, request the missing task; do not select one automatically.}

1. Ground the task: confirm cwd and Git repository, inspect status, preserve unrelated changes, read applicable repository instructions and the task's acceptance criteria. For an issue, read its current body and relevant comments and respect actual blockers/dependencies. Search exact symbols and references before reading the smallest relevant fragments.
2. Draft a short requirement-to-change-and-check plan yourself. Identify only decisions essential to implementation. Classify the proposed changes, not keywords: migrations, security boundaries, changes to shared-state/concurrency invariants, broad API/compatibility changes, and material unresolved risk use the risky route. An ordinary task does not need an independent plan review in this experiment. This omission is deliberate and must be recorded in the measurement note.
3. Optional scout: only if a concrete repository question remains unanswered and an independent lookup would unblock the next step, invoke at most ONE foreground `subagent` with `agent: "ix-scout"`, `task: "<one exact question, known files/symbols, evidence already checked, and what answer will unblock>"`, `options: { context: "fresh" }`, `async: false`. Do not send the entire task for general reconnaissance. If no such question exists, skip scouting. Use the named role directly; do not enumerate agents unless the tool reports it missing. The scout's eight-call budget is an instruction, not a runtime-enforced limit: record actual calls/duration and any overrun. Verify contradictions and missing evidence yourself; do not rerun scouts or repeat a repository tour.
4. Risky route before implementation: use read-only `planner` (Luna/high) followed by `plan-reviewer` (Sol/high), foreground `async: false`, `options: { context: "fresh" }`. Supply requirements, current evidence, proposed plan, risks and constraints. The plan-reviewer brief must include `RUN_PLAN_REVIEW: true`, `CURRENT TASK`, and `PROPOSED PLAN`. Confirm material findings against code/contracts or a focused check. Correct ordinary plan details yourself; use planner for risky corrections. At most one focused follow-up for a materially changed plan; report remaining material blockers. Do not treat a reviewer verdict as proof or guess past unresolved risk.
5. You are the only code writer. Implement in the parent session, keep scope focused, and reassess risk before changes that introduce new risky behavior. Routine implementation choices within the contract are yours. Do not silently narrow an explicit requirement, substitute a familiar convention, or treat documentation/tests of an exception as user approval of it. Preserve safe independent work when a decision remains open; never claim the unresolved requirement complete.
6. Verification: select tests by changed behavior, contracts, call sites and consumers, not only filenames or diff size. For isolated changes with known boundaries, run relevant module/consumer tests and success/error paths plus applicable build/lint; do not default to the full suite. Explain coverage and gaps. Broader/full checks are needed for releases, broad refactors, shared interfaces/data formats, dependencies, test/runtime infrastructure, shared-state/concurrency or security invariants, uncertain impact or evidence of a wider regression. Repository/user-required checks remain mandatory. Run focused checks and applicable build/lint before review; if a full suite is needed, run it after review fixes on the ready implementation. Reuse earlier evidence only where later changes do not affect checked behavior. After a test-only addition/correction run that test or file; after a local code fix rerun affected checks and applicable build/lint. Repeat a full suite only for a new impact reason above or an explicit requirement, and state why. Capture actual exit codes; with tail/tee use pipefail in a supported shell or capture the check status before printing its log. Keep required checks enabled and distinguish a failing suite from a passing focused check. Diagnose a known baseline failure again only for changed symptoms/code/environment or missing evidence. For a coverage gap run the smallest useful check. Never spend a fixed writing budget and stop at an intermediate milestone.
7. For a non-trivial implementation, run ONE independent read-only code review: `reviewer` (Haiku/medium) for ordinary work; `reviewer-sol` (Sol/high) for risky work or risk introduced by the diff. Use foreground `async: false`, `options: { context: "fresh" }`, with the original requirements, accepted plan, relevant diff, concrete verification and all contract exceptions/gaps. Require evidence for important findings, confirm them yourself, fix confirmed defects and rerun affected checks. If cheap review uncovers a newly confirmed/material unresolved risk, allow one focused Sol escalation; record its reason. No cosmetic review loops. Mechanical wording-only work may skip this review and be verified directly.
8. Finish with a compact acceptance map AFTER fixes: requirement → implementation location → concrete check/result → status. Use exactly these meanings: `verified` (implemented and checked), `verification-gap` (implementation evidence exists but checking is incomplete), `contract-exception` (implementation is narrower/different), `not-implemented`. List every exception explicitly. Reviewer approval, test count, and documenting a limitation do not convert an exception into fulfillment. If a referenced standard was not checked, record that verification gap. Fix a material mismatch or report it as incomplete; do not silently rewrite acceptance criteria.
9. Report the practical result, evidence and remaining gaps in the user's language. Do not automatically push, merge, deploy, close issues, change queues or make unrelated external writes. Follow stricter user/repository boundaries for local commits. Complete all authorized safe local work before stopping. In the measurement note record: main model/thinking, ordinary/risky route, scout skipped or exact question plus actual calls/time, review agents, useful findings/fixes, human interventions, elapsed and total parent+child usage/cost only if reliably available (otherwise unavailable). Do not hunt unrelated session files for telemetry or double-count child usage.

This is an opt-in prompt policy, not an enforced gate. A real comparison is required before claiming it faster, cheaper, or safer than `/i`.
