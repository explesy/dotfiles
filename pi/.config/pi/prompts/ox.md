EXPERIMENTAL ORCHESTRATION (`/ox`). This is an opt-in A/B experiment, NOT `/n`, `/i`, `/p`, or `/c`. Do not call or modify those commands. Keep the current model and thinking level, and do not change agent mappings or project backlog/queue.

TASK: ${ARGUMENTS:-Use the concrete task already specified in this conversation. If there is no unambiguous task, request one; never select an issue automatically.}

Run this experiment end-to-end, but do not widen the requested scope:

1. Confirm the working directory is the intended Git repository. Inspect `git status` and the relevant repository instructions, and preserve unrelated modifications. If TASK refers to a GitHub issue, read it and obey its acceptance criteria and blocked/gated/dependency restrictions. Stop on an actual blocker. Do not auto-select a different issue.
2. Resolve the existing global workflow file to an absolute path: `$PI_CODING_AGENT_DIR/workflows/ox-scouts.js`, or `~/.config/pi/workflows/ox-scouts.js` if the environment variable is unset. Submit **one** foreground `subagent` call with `workflow` equal to that absolute file path, `args: { task: "<the exact concrete task and any issue context needed>" }`, `async: false`, and `options: { context: "fresh" }`. Do not use removed `workflowScript`/`workflowScriptPath`, top-level `parallel`/`tasks`, `workflow: true`, or `clarify`. The workflow starts two read-only `scout` children concurrently using `runs.all`. If the tool fails or either child fails, report the failure and stop rather than pretending scouting succeeded.
3. Merge the two scout reports into a small implementation plan grounded in verified code, cross-check contradictions, and explicitly identify any missing essential decision. Use the scout map to read only necessary implementation fragments and verify disputed or missing evidence; repeat broader investigation only for a concrete contradiction or gap. No automatic expensive planner/plan-reviewer escalation in this experiment. If implementation would be unsafe without an important decision, report the blocker rather than guessing.
4. **You are the only writer.** Implement the task in this parent Pi session using the existing selected main model. Do not launch writing subagents, do not change unrelated files, do not silently change user model/routing configuration. Do not impose a small hard step limit or stop at an intermediate milestone.
5. Run focused tests/checks, then broader checks only if warranted. After non-trivial changes, run exactly one independent `subagent` call with `agent: "reviewer"`, `options: { context: "fresh" }`, `async: false` and a self-contained brief: task, acceptance criteria, changed files/diff, completed tests and known risks. `reviewer` is read-only. Fix valid blocking/important findings and re-run affected tests. No endless review cycle and no automatic expensive reviewer.
   - Select tests by changed behavior, contracts, call sites and consumers, not only filenames or diff size. For isolated changes with known boundaries, run relevant module/consumer tests and success/error paths plus applicable build/lint; do not default to the full suite. Explain coverage and gaps. Broader/full checks are needed for releases, broad refactors, shared interfaces/data formats, dependencies, test/runtime infrastructure, shared-state/concurrency or security invariants, uncertain impact or evidence of a wider regression. Repository/user-required checks remain mandatory.
   - Run focused checks and applicable build/lint before review; if a full suite is needed, run it after review fixes on the ready implementation. Reuse earlier evidence only where later changes do not affect checked behavior. After a test-only addition/correction run that test or file; after a local code fix rerun affected checks and applicable build/lint. Repeat a full suite only for a new impact reason above or an explicit requirement, and state why.
   - Capture actual check exit codes. For output piped through tail/tee, use pipefail in a supported shell or capture the check status before displaying the log. A successful log-printing command does not prove the check passed.
   - Give the reviewer a requirement-to-code-and-check map. Ask it to prioritize acceptance violations, required input fields, contract-valid exceptional paths, and preserved behavior. A confirmed requirement violation is at least important even if rarely triggered. Confirm material findings against code/contracts or a focused check before fixing them.
   - Record previously confirmed baseline failures and their evidence. Repeat baseline diagnosis only for changed symptoms, relevant code/environment, or unavailable evidence. Keep required checks enabled and report any failing full suite honestly.
   - After review fixes, verify each acceptance requirement against its implementation location and a concrete check/result. For a coverage gap, run the smallest meaningful check; report any unverified requirement instead of claiming full completion. Test counts and reviewer approval do not replace this final map.
   - Label each requirement verified, verification-gap, contract-exception, or not-implemented. List all limits/exceptions relative to the original task; documenting or testing an exception does not authorize weakening the requirement. Fix material mismatches or report incomplete work. Record an unverified referenced standard as a verification gap. Routine choices within the contract remain yours.
6. Do not automatically push, merge, deploy, close the issue, or advance GitHub execution queues. Follow any stricter repository/user approval boundaries. Report what was actually completed, tests and review verdict, remaining blockers, and a brief A/B measurement note: wall-clock elapsed and tokens/cost only if reliably available (otherwise say unavailable). Do not claim a live test passed without evidence.

Keep the result practical and concise: human outcome first, technical evidence second. This command keeps its separate orchestration; shared reviewer instructions also apply to other workflows that invoke that agent.
